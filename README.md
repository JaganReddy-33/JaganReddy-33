### 💡 The problem

Seatline is built around a real backend engineering problem:

> **What happens when many users try to book the same seat at exactly the same time?**

A normal CRUD implementation can easily create a race condition where two requests observe the same available seat before either request updates it.

Seatline approaches the problem at the **database and system-design level**, rather than relying only on frontend checks.

### ⚙️ Engineering focus

| Area             | Implementation                    |
| ---------------- | --------------------------------- |
| ⚛️ Atomicity     | Atomic MongoDB operations         |
| 🔄 Concurrency   | Race-condition aware booking flow |
| 🔑 Idempotency   | Idempotency keys for safe retries |
| 📡 Real-time     | Socket.IO synchronization         |
| 🔐 Security      | JWT authentication                |
| 👥 Authorization | Role-based access                 |
| 🧪 Reliability   | Load-test driven verification     |
| 🗄️ Persistence  | MongoDB                           |

### 🧠 What this project demonstrates

```text
Client Request
      │
      ▼
Authentication
      │
      ▼
Booking API
      │
      ▼
Concurrency Validation
      │
      ▼
Atomic Database Operation
      │
      ├──────► Booking succeeds
      │
      └──────► Conflicting request rejected
                     │
                     ▼
              Real-time update
                     │
                     ▼
               Connected clients
```

The goal isn't simply:

```text
"User clicked → seat booked"
```

The goal is:

```text
"Many requests → one valid state → predictable result"
```
